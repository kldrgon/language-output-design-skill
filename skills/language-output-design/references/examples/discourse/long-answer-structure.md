# 长回答结构案例

## 先给结论再展开证据

**场景**  
用户询问是否应该升级数据库版本。用户已经知道当前版本存在性能问题，但不确定升级的风险和收益。

**原文**

> 数据库升级是一个复杂的过程。首先，我们需要考虑兼容性。其次，我们需要评估性能改进。此外，还需要考虑迁移成本。另外，团队经验也很重要。最后，还需要考虑回滚方案。综上所述，升级需要谨慎考虑。

**问题**  
没有先给出结论，读者需要读完整个段落才能知道建议。多个因素并列出现，没有说明哪个是决定性条件。

**改写**

> 建议先停留在当前版本，因为升级的收益不足以抵消迁移风险。  
>   
> 当前版本的性能问题可以通过索引优化解决，不需要升级。新版本虽然提供了更好的查询优化器，但迁移需要修改 20% 的 SQL 语句，并且团队对新版本的运维经验不足。  
>   
> 如果未来需要用到新版本的 JSON 函数，再评估升级。届时应先在一个非关键服务上试点，验证兼容性和性能。

**改写依据**  
先给结论，再说明决定性条件，最后给出例外情况。读者可以快速判断是否需要继续阅读。

## 主线未闭合就进入支线

**场景**  
用户询问如何优化慢查询。用户已经提供了查询语句和执行计划，但不确定优化方向。

**原文**

> 这个查询可以优化。索引是数据库性能的关键。索引有很多种，例如 B-tree、哈希索引和全文索引。B-tree 索引是最常见的，它使用平衡树结构。平衡树是一种自平衡的二叉搜索树，它的插入和删除操作的时间复杂度是 O(log n)。因此，这个查询需要优化。

**问题**  
主线只说到“可以优化”，就进入索引类型的细节，原本要解释的优化方向没有完成。

**改写**

> 这个查询可以通过添加复合索引优化。当前查询在 `WHERE` 子句中使用了 `user_id` 和 `created_at`，但只存在 `user_id` 的单列索引。添加 `(user_id, created_at)` 的复合索引后，查询可以直接定位到目标范围，避免全表扫描。  
>   
> 索引类型的选择取决于查询模式。B-tree 索引适合范围查询，哈希索引适合等值查询。当前查询需要范围过滤，因此 B-tree 是合适的选择。

**改写依据**  
先完成优化方向和机制，再说明索引类型的选择依据。支线被放在主线之后，没有抢占当前解释。
